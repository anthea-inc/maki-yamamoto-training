## 課題 1

- React コンポーネントにおける state の基本的な役割について説明してください。

役割：UI の「現在の状態」を管理し、それに応じて画面を再描画すること

1. 状態の保存
   → state は、ボタンがクリックされた回数や、入力フォームに入力された値、API から取得したデータなど、時間とともに変化するデータを保存するために使う

2. UI の動的更新
   → React は仮想 DOM を使っているため、state が更新されると、自動的に変更があった部分だけが再描画される
   これにより、効率的に UI を更新することができる

3. コンポーネントごとに独立
   → state は基本的にそのコンポーネント自身だけで管理されるローカルな状態
   他のコンポーネントから直接アクセスすることはできない（props を使ってやりとりする）

- state と props の違いを明確にし、それぞれの使い分けについて解説してください。

-- state と props の違い --

管理者
state：コンポーネント自身が管理
props：親コンポーネントが管理

変更可否
state：変更可能（useState などで更新）
props：読み取り専用（変更不可）

用途
state：内部状態の保持・変更
props：外部から渡されるデータやコールバック関数の受け取り

更新トリガー
state：コンポーネント内のイベントや処理によって更新される
props：親コンポーネントの state やロジックによって変化

-- 使い分けのポイント --

state を使う場面
・入力フォームの値を保持する
・モーダルの開閉状態を管理する
・ボタンのクリックの回数など、コンポーネント内で完結する状態

props を使う場面
・親コンポーネントから子コンポーネントにデータを渡す
・子コンポーネントにイベントハンドラ（関数）を渡す
・データの流れを「一方向に保つ」（トップダウン）

メモ：
モーダルとは？
ユーザーの画面に一時的に浮かび上がるダイアログやウィンドウで、背景のコンテンツ操作を一時的にロックし、ユーザーに特定の操作を促すために使われる

## 課題 2

- state の更新が非同期であるとは具体的にどういうことか説明してください。

「非同期」という言葉は、処理の完了を待たずに次の処理が進むという意味
たとえば、setState を呼び出しても、その直後に state を確認してもまだ古い値のままということがよくある

【index.jsx】
const [count, setCount] = useState(0);

const handleClick = () => {
setCount(count + 1);
console.log(count); // まだ古い値が出力される（更新されていない）
};

メモ：
この場合、setCount(count + 1)で state を更新しようとしているが
console.log(count)はまだ更新前の古い値（例えば 0）を表示してしまう

なぜ非同期なのか？🧐
💡React がパフォーマンス最適化のために state の更新をバッチ処理しているから

React は複数の state 更新をまとめて一気に処理することで、レンダリング回数を最小限にするようにしている
そのため、setState や setCount のような関数は、即時に state を変えるのではなく、後でまとめて処理するように設計されている

- state の非同期更新が原因で発生しうる問題点を挙げ、それを回避するための注意点を解説してください。

問題点１
古い state を使ってしまう

【index.jsx】
const [count, setCount] = useState(0);

const handleClick = () => {
setCount(count + 1);
setCount(count + 1);
};

このコードは「2 回加算」したいように見えるが、実際には 1 だけ増えることがほとんど
setCount は即時に実行されるのではなく、後で 1 回の更新としてまとめられてしまうことが原因

問題点２
状態が最新だと思って処理を書くと意図通りにならない

【index.jsx】
const handleSubmit = () => {
setIsSubmitting(true);
if (isSubmitting) {
console.log("もう送信中です"); // 期待通りに表示されないことがある
return;
}
};

setIsSubmitting(true)を呼んだ直後には、isSubmitting はまだ更新されていない
つまり「送信中フラグが立っていない」とみなされ、重複送信が発生するリスクがある

- state を更新する際に、更新用関数を使用するべき理由と、その利点を説明してください。

React の setState（または useState の更新関数）には、次のように関数を引数として渡すことができる
この prevCount => prevCount + 1 のような書き方を「関数型の更新関数」という

【index.jsx】
setCount(prevCount => prevCount + 1);

-- 使用するべき理由と利点 --

1. 最新の state に基づいて安全に更新できる

【index.jsx】
// 通常の（値に基づく）更新
setCount(count + 1);
setCount(count + 1);

React では state 更新が非同期でバッチ処理されるため、上記のようなコードでは期待と異なる挙動になる
count が例えば 0 の場合、2 回加算したいのに最終的に 1 にしかならないことがある

【index.jsx】
// 関数型更新を使った例
setCount(prev => prev + 1);
setCount(prev => prev + 1);

この場合、React はそれぞれの prev を最新の状態として評価してくれるため、結果は正しく 2 増える

2. 複数の更新が順番通り安全に処理される
   → 関数型の更新は、React が更新をキューに追加し、順番に評価するため、他の state 更新との競合を防げる
   これにより、複雑な状態管理でも予測可能な動作を得ることができる

3. 副作用や外部の非同期処理と組み合わせやすい

ユーザーの操作が非同期イベント内で複数回発生するような場合にも、常に最新の状態で更新できるので、安心して使える
通常の setItems([...items, newItem])だと、古い items を元にしてしまい、新しいアイテムが消える可能性がある

【index.jsx】
fetchData().then(() => {
setItems(prevItems => [...prevItems, newItem]);
});

## 課題 3

- state に保持しているオブジェクトや配列を直接変更してはいけない理由を説明してください。

React は state や props の変更を検出するために、前回の値と現在の値を比較する
その比較は、基本的に参照（オブジェクトのポインタ）で行われる

問題点
user.age = 24 のように中身だけ変えても、user というオブジェクトの参照自体は変わっていない
そのため、React は「変更がない」と判断し、再レンダリングしない
結果、UI が更新されない、バグが発生する

【index.jsx】
const [user, setUser] = useState({ name: "Maki", age: 25 });

// NG 例: 直接変更している
user.age = 24;
setUser(user); // 見た目上は変更している

// OK 例: 新しいオブジェクトを作って更新
setUser(prev => ({
...prev,
age: 24,
}));

メモ：
直接変更とは？
React の state に格納されたオブジェクトや配列を、イミュータブル（不変）に扱わず、元の参照のまま中身を変更すること

- 直接変更が引き起こす可能性のある具体的なバグや問題を解説してください。

1. 再レンダリングが起こらない
   → オブジェクトの参照が変わっていないため、React は「state は変わっていない」と判断する

2. 同じ state を参照している他の変数にも影響する（副作用）
   → フォームやカスタムフックなど複数のコンポーネントで state を共有しているときに、予期しない挙動や難解なバグの原因になる

3. 状態比較（差分検出）が正しく動作しない
   → 参照が変わらないため、useEffect が再実行されない

- オブジェクトや配列の state を「イミュータブル（不変）」に更新するための方法を、コード例と共に示してください。

-- オブジェクトのイミュータブル更新 --

例 1：オブジェクトの特定のプロパティを変更する
【index.jsx】
const [user, setUser] = useState({ name: "Maki", age: 25 });

// age だけ更新したい場合
setUser(prevUser => ({
...prevUser, // 既存のプロパティをコピー
age: 24 // 上書きするプロパティだけ指定
}));

-- 配列のイミュータブル更新 --

例 2：配列に要素を追加する
【index.jsx】
const [fruits, setFruits] = useState(["apple", "banana"]);

// "orange" を追加
setFruits(prevFruits => [...prevFruits, "orange"]);

## 課題 4

- コンポーネントの state を設計する際に、どのような点を考慮すべきか説明してください。

コンポーネントの state を設計する際には、後々の保守性・パフォーマンス・バグの予防につながる重要な設計判断が含まれる
ただ「データを持たせる」だけでなく、どう持たせるか・持たせないかまで考えることが重要になる

1. state に「必要最小限のデータ」だけを持たせる
   → UI に直接必要な情報だけを持たせる

2. state はできるだけ単純な構造に保つ
   → ネストが深いオブジェクトや複雑な構造はバグを招きやすい

3. 非同期更新とバッチ処理を意識する
   → state の更新は非同期なので、前の状態に依存するなら関数型更新を使う

4. 状態のリセットしやすさを考慮する
   → フォームなどで「リセット」や「初期化」が必要になるケースでは、初期状態を定数として定義しておくと便利

- 複数のコンポーネントで同じ state を共有・編集する必要が生じた場合、どのようなアプローチを取るべきか解説してください。

２つのコンポーネント間で共有（親子 or 兄弟）
→ 状態を親コンポーネントにリフトアップ（リフトステートアップ）

多くのコンポーネントで共有
→ コンテキスト API（React Context）を使用

メモ：
リフトアップ（リフトステートアップ）とは？
React において複数のコンポーネントで共有したい state を、最も近い共通の親コンポーネントに移動（＝“持ち上げる”）することを指す
この概念は、React の公式ドキュメントでも強調されており、データの一貫性と UI の同期を保つための基本的なテクニック

- ステートのリフトアップの概念を説明し、その具体的な実装方法を示してください。

ステートのリフトアップとは？
通常、useState などで状態を定義すると、その状態はそのコンポーネントのローカル（内部）状態になる
しかし、2 つ以上の子コンポーネントで同じデータを使いたい・同期させたいとき、それぞれが個別に状態を持っていると、状態がずれたり、予期せぬ挙動が起きる可能性がある

そこで、「その 2 つの子コンポーネントの共通の親コンポーネント」に state を移動し、そこから必要な情報や操作関数を子に渡すという方法を「リフトアップ」という

【実装方法　手順】
① 共有すべき状態を明確にする
まずは、どのコンポーネント間で同じ状態を使いたい／共有したいのかを洗い出す
例：「A で入力した名前を B に表示したい」

② 状態を最も近い共通の親に移動する
共有対象となる状態（state）は、それを使う複数のコンポーネントの最も近い共通の親コンポーネントに持たせる
・状態の実体（useState など）を、親コンポーネントの中に定義する

③ 子コンポーネントに props 経由で渡す
親で定義した状態や、状態を更新するための関数を、props として子コンポーネントに渡す
・表示だけ必要なら値だけを渡す
・編集・更新もさせたい場合は、更新関数（例：setText）も渡す

④ 子は props を使って状態を使う or 変更する
子コンポーネントは自身では状態を持たず、受け取った props を使って状態を利用・変更する
・子はあくまで「受け取って使う」役割に徹する
・状態の所有者は常に親
