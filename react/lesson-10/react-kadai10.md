## 課題 1

- CSS in JS の基本的な概念について説明してください。

CSS in JS とは？
JavaScript の中に CSS スタイルを記述する技法で、主に React などのコンポーネントベースのライブラリやフレームワークと一緒に使われる

1. JavaScript の中でスタイルを書く
2. スタイルを動的に変更できる
3. スコープがコンポーネント単位

- ランタイム CSS in JS とゼロランタイム CSS in JS について、それぞれの仕組み、主な特徴、および両者の主な違いを比較しながら具体的に説明してください。

1. ランタイム CSS in JS

仕組み
・コンポーネントが実行時（ランタイム）に読み込まれる際に、JavaScript で CSS を生成する
・実行時にスタイルの文字列を組み立てて <style> タグとして DOM に挿入する

代表的なライブラリ
・styled-components
・Emotion（default 設定の場合）

主な特徴

柔軟性
→ 動的スタイル（props による条件分岐など）に非常に強い

ランタイムコスト
→ 実行時に CSS を生成するため、初回レンダリング時のパフォーマンスが低下することがある

SSR 対応
→ 一部ライブラリでは Server Style Sheet などで対応しているが、実装の工夫が必要

---

メモ：
SSR とは？
SSR（Server Side Rendering）は、ウェブアプリケーションにおいて「サーバー側で HTML を生成してクライアントに送る方式」のことを指す
これは、SPA（シングルページアプリケーション）のような「クライアントサイドレンダリング（CSR）」とは対照的なレンダリング方式

SSR の仕組み

1. ユーザーがページにアクセス
2. サーバーがそのリクエストを受け取り、React などのフレームワークを使って HTML をサーバー上で生成
3. 生成された HTML がユーザーのブラウザに送られ、即座に描画
4. その後、JavaScript が読み込まれて、クライアント側でインタラクティブな処理が有効化（ハイドレーション）

---

2. ゼロランタイム CSS in JS

仕組み
・スタイルをビルド時に静的に抽出し、CSS ファイルとして出力する
・実行時にスタイルを生成する処理がなく、ただの CSS クラスとして HTML に適用される

代表的なライブラリ
・vanilla-extract
・Linaria
・Astro + Tailwind（CSS in JS ではないが似た思想）
・compiled（Meta 製）

主な特徴

柔軟性
→ 動的スタイルは制限がある。テーマの切り替えなどは仕組みが必要

パフォーマンス
→ 実行時の CSS 生成がないため、表示が早くパフォーマンスに優れる

型安全性
→ TypeScript との相性がよく、型付きでスタイルを記述できることが多い

デプロイサイズ
→ CSS がビルド時に最適化されるため、ファイルサイズが小さくなることが多い

---

## 課題 2

- CSS Modules の仕組みと主な特徴について説明してください。

-- 仕組みと流れ --
CSS Modules は、通常の CSS ファイルを ローカルスコープで扱うための技術
つまり、クラス名やセレクタが自動的にユニークな名前に変換されることで、スタイルの衝突を防ぐ仕組みになっている

1. .module.css や .module.scss などの拡張子が付いたファイルを対象にする
2. ビルド時（例：Webpack など）、クラス名が一意なハッシュ付きクラス名に変換される
   → 例：.button → .Button_xyz12abc
3. JavaScript 側では、その変換後のクラス名をインポートして利用できる

-- 主な特徴 --

1. ローカルスコープ
   → クラス名がコンポーネント単位で閉じているため、同じ名前のクラスを複数のモジュールで自由に使える

2. ネーミング競合を防ぐ
   → 一意なハッシュ名が付くので、異なるファイル間でのクラス名の衝突が発生しない

3. 型安全性との相性が良い
   → TypeScript を使う場合、CSS Modules に型定義を加えることで、クラス名のタイプチェックが可能になる

- CSS Modules が、従来の CSS 開発におけるどのような問題を解決するために考案されたのか、その背景も含めて説明してください。

-- 従来の CSS 開発の課題 --

1. グローバルスコープ問題

CSS では、クラス名や ID はすべてグローバルスコープに存在する
つまり、異なるファイルやコンポーネント間でクラス名が衝突するリスクがある

以下のように、クラス .button が複数のファイルで定義されていると、後から読み込まれたスタイルで上書きされるという現象（スタイルの副作用）が発生する

【index.css】
/_ reset.css _/
.button {
margin: 0;
}

/_ header.css _/
.button {
padding: 10px;
}

2. 可読性・保守性の低下

プロジェクトが大規模になると、どの CSS クラスがどこで使われているかの追跡が困難になる
・クラス名のルールが曖昧
・スタイルの再定義が発生しやすい
・無駄な CSS の肥大化（デッドコード）

-- CSS Modules の登場と解決したこと --

1. グローバルスコープの排除
   → 各 CSS クラスをローカルスコープに閉じ込めることで、同じクラス名でも干渉しない構造を実現

2. 自動でユニークなクラス名に変換
   → 開発者はシンプルなクラス名を書くだけで、ビルド時に自動的にユニークに変換される

3. スタイルとコンポーネントの密結合
   → CSS ファイルとコンポーネントファイルを一対一にできるため、関心の分離（Separation of Concerns）を保ちつつ、関連性を高められる

4. スタイルの可視性・追跡性の向上
   → 使用するクラス名が JS 側からインポートされているので、IDE で補完が効く、
   未使用のスタイルを検出しやすい など、保守性が向上

## 課題 3

- Tailwind CSS の基本的な考え方（例：ユーティリティファースト）と主な特徴について説明してください。

ユーティリティファーストとは、「再利用可能な CSS クラス（ユーティリティクラス）を HTML に直接適用してデザインを構築する」手法のことを指す

-- Tailwind CSS の主な特徴 --

1. ユーティリティクラスの豊富さ
   → レイアウト、フォント、余白、色などに関する 1,000 以上のユーティリティクラスが用意されており、柔軟かつ詳細なデザインが可能

2. デザインシステムへの適合性
   → tailwind.config.js によって、独自のテーマ（カラー、フォント、間隔など）を定義できる
   これにより、一貫したデザインルールをチーム全体で保てる

3. パフォーマンス重視のビルド（JIT モード）
   → Tailwind の Just-In-Time（JIT）モードでは、使ったクラスだけをビルド時に CSS に出力するため、最終的な CSS ファイルは非常に小さくなる

4. クラスの命名不要
   → BEM や OOCSS などの命名規則を考えなくても、ユーティリティクラスだけでスタイルを適用できるため、命名の悩みから解放される
   コメント：命名するたびに迷ってしまうので、それはとても良い 👌

メモ：
ユーティリティクラスとは？
一つのクラスが、たった一つのスタイルプロパティだけを担うように設計された CSS クラスのこと

- Tailwind CSS を利用するメリットとデメリットを、それぞれ具体例を挙げながら説明してください。

-- メリット --

1. 開発スピードが速い
   → ユーティリティクラスを HTML に直接書けるため、スタイルを書くために CSS ファイルを開く必要がない

2. CSS の肥大化・重複が防げる
   → 必要なクラスだけを使う設計＋ JIT（Just-In-Time）コンパイルにより、未使用の CSS はビルド後に自動で削除される

3. 一貫したデザインにしやすい
   → tailwind.config.js でカスタムテーマを定義できるため、カラーやフォント、余白などをプロジェクト全体で統一できる

メモ：
tailwind.config.js とは？
Tailwind CSS の動作やデザインシステムをカスタマイズするための設定ファイルのこと
このファイルを使うことで、Tailwind の標準スタイル（色、フォント、ブレークポイントなど）を自分のプロジェクトに合ったものに拡張・上書きできる

-- デメリット --

1. HTML が長く・読みにくくなることがある
   → ユーティリティクラスを多数並べると、HTML タグが増え、パッとみて何をしているのか分かりにくくなる

2. クラス名を覚えないといけない
   → 最初は mt-4 や text-lg などの命名ルールに慣れる必要がある（違いがわかりづらい）

3. JIT ビルド環境が必要（静的 HTML には不向きなケースも）
   → Tailwind の恩恵を最大限に受けるには、Vite、Webpack、Next.js などのビルドツールの導入が前提となる

## 課題 4

- 大規模な Web アプリケーションを新規開発するチームに参加したと想定し、CSS in JS/CSS Modules/Tailwind CSS の中からどの手法を採用するか、その理由も含めてあなたの考えを明確に説明してください。（正解は一つではありません。あなたの考えと根拠を重視します。）

大規模アプリの新規開発においては、私は「Tailwind CSS」を採用します。
「スピード・一貫性・保守性」という観点で、大規模開発における強力な選択肢だと考えています。

理由は以下のとおりです：
・UI 一貫性をコードで管理でき、デザインガイドラインを保ちやすい
・命名の迷いやルール調整の必要がなく、チーム開発に向いている
・パフォーマンス最適化（JIT）が標準対応で軽量なアプリを構築しやすい
・コンポーネントベースと親和性が高く、拡張しやすい構造

補足メモ：
学習コストは高いが、慣れてしまえば従来の CSS を使用するより開発スピードが上がるのは良い

残しておきたいメモ：
見た目を綺麗にするためだけに「＠apply」を使用しない
・コンポーネント化にはクラス名を考える必要がある
・変更の際に複数のファイル間の移動が必要となる
・コンポーネント内の値を変更した際にサイト内の他の部分が壊れる可能性がある
・コンポーネント化はボタンなど小規模で再利用性の高いもので行う

-- 実践課題５ --

通常のCSS（グローバルCSS）
メリット：すぐに使えてシンプル
デメリット：クラス名の衝突を意識しないといけない

CSS Modules（ランタイム CSS）
メリット：一意なクラス名が自動で付与される。従来の CSS と書き方が変わらないため、学習コストが低め
デメリット：CSS ファイルと JS ファイルで分離してしまうため、管理コストが高め

メモ：
将来的に非推奨になるリスク
React や Vue.js などコンポーネント指向を重視する言語が増えたことで、再度注目されることになった CSS modulesの歴史は長く、古めの技術となりつつある
そのため、メンテナンス面でサポートされなくなるリスクに晒されている
移行しやすい設計を常に意識した方が良い

注意
・CSS コンポーネント → 解析 → JSX 生成 → 解析 → HTML 出力
→ ライブラリによる解析とブラウザによる解析が2回起こる

-- Panda CSS（CSS-in-JS） --
メリット：JavaScriptの中でスタイルが完結するのが良い
デメリット：新しい概念を覚える必要がある。JSとCSSを習得する必要がある

-- Tailwind CSS（ゼロランタイム CSS） --
メリット：CSSファイルのサイズを小さくできる
デメリット：ユーティリティクラスを組み合わせると指定するクラスが多くなり、情報量が増えるため、可読性が落ちる
→ clsxライブラリを使ったり、再利用パターンを整備することで十分にカバーできる

メモ：
clsxとは？
Tailwind CSSやReactのようなJSX内でクラス名を動的に切り替えたいときに便利なライブラリ
複雑なclassNameをシンプルに管理できる

まとめ
私が選んだのは「Tailwind CSS（ゼロランタイム CSS）」でした🥳
理由：
・スタイルがJSXに集約され、他ファイルに行き来しなくても完結できる（生産性が高い）
・規模の大きな開発やチーム開発でも、影響範囲が明示的で管理しやすい
・パフォーマンスに優れ、実運用に向いている
→ 使っていないスタイルはJITによって削除される
